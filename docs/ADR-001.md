# ADR-001 — Baseline Interoperability & Security

- **Project:** Custom VPN Platform (iOS-first, separate protocol daemons)
- **Status:** Proposed — pending Phase 0 verification; not approval to deploy
- **Date:** 2026-10-17
- **Applies to:** Phase 0 and Phase 1; constraints carried into Phases 2–4
- **Inputs:** Custom VPN PRD v0.3; Phase 0 TDD v0.2
- **Decision owner:** Project maintainer

## 1. Context

The platform must run an independently implemented Rust IKEv2/IPsec responder on Ubuntu LTS and connect using the native iOS VPN client, later the native Windows client. ESP data-path processing is delegated to Linux kernel XFRM; no third-party VPN server or client application is introduced. Accounts authenticate using username/password (EAP-MSCHAPv2); the server authenticates with an X.509 certificate. No device registration, device limits, device-specific credentials or device-based revocation are permitted. Phase 1 is a single-node, file-configured MVP with **no control-plane API**; Phase 2 adds a private control plane.

An IKEv2 implementation operates at a security-critical protocol boundary. We need explicit choices and a reproducible test gate before trusting the design.

## 3. Decisions and rationale

### D1 — Rust IKEv2 control plane, Linux XFRM ESP data plane

**Decision.** Write our own strict IKEv2 parser, message generation, state machine, key derivation integration, EAP orchestration and SA lifecycle in Rust. Use established cryptographic libraries rather than writing AES, SHA, ECDH or RSA primitives. Program kernel ESP states and policies via NETLINK_XFRM. Linux performs ESP encryption, integrity/replay handling and packet transforms.

**Alternatives rejected.** Full userspace ESP implementation (more attack surface, performance and kernel networking complexity); launching a third-party VPN daemon (violates product ownership constraint).

**Consequences.** Ubuntu/Linux kernel dependency; XFRM privilege and failure cleanup must be engineered and tested. Kernel APIs and IKEv2 logic are independent modules.

### D2 — Supported protocol and client scope

**Decision.** First release exposes an IKEv2 responder on UDP 500/4500. iOS must connect via the built-in VPN stack and a manually provisioned `.mobileconfig`; Windows support follows through the *same* responder. SSTP, if pursued, lives in another process and is not part of Phase 1.

**Rationale.** Native client interoperability without third-party applications and clear daemon boundaries.

**Consequence.** Native iOS behavior—not an abstract RFC-only implementation—is the acceptance gate. Interop tests must capture the actual proposals and configuration payload behaviors of supported iOS versions.

### D3 — Identity and authentication

**Decision.** The responder authenticates to the client using an X.509 **IKEv2 AUTH** signature and trusted server certificate. The user authenticates with EAP-MSCHAPv2 username/password, without client certificates. The implementation must correctly complete the EAP/IKE_AUTH sequence and provide MSCHAPv2 mutual method confirmation. Reject unauthenticated CHILD_SA creation.

**Alternatives rejected.** Client certificate or device-specific identity (conflicts with requirements); PSK-only and undocumented custom password mechanisms (interop/security mismatch).

**Important distinction.** IKEv2 is **not TLS**. The certificate proves server identity during IKE authentication; it is inaccurate to specify a TLS server listener on UDP 500/4500.

**Risks.** MSCHAPv2 carries known password-guessing weaknesses, especially if an attacker obtains a challenge/response or password-equivalent verifier. Require long, unique passwords; certificate validation; authentication throttling; and careful secret handling. Do not describe EAP-MSCHAPv2 as providing the properties of modern password-authenticated key exchange.

### D4 — Algorithm baseline and negotiation

**Decision direction.** Prefer AEAD such as AES-GCM for IKE/ESP, a SHA-2-family PRF appropriate for IKE, and a well-supported modern Diffie-Hellman group. Do **not** lock an unverified single proposal, assume AES-GCM requires a separate integrity transform, or conflate IKE SA and CHILD SA transforms. The responder must validate all negotiated transform attributes, key sizes, AEAD nonce/salt structure and initiator/responder preferences.

**Provisional test candidates (not final mandatory suite):**
- IKE SA: AES-256-GCM or AES-128-GCM with an appropriate SHA-2 PRF and negotiated DH group (e.g. ECP-256 / group 19), subject to client support.
- CHILD SA: ESP AES-GCM with correct integrity transform handling and negotiated traffic selectors.
- PFS for later CHILD SA rekeys where negotiated; the initial CHILD SA derives key material as defined by IKEv2 and must not be modeled as an independent mandatory DH exchange.

**Validation gate.** Record an exact transform compatibility table with IANA IDs, offered algorithms, chosen algorithms, iOS build, Ubuntu kernel crypto support, and Windows follow-up considerations. Use RFC 7296 and current IKEv2 algorithm guidance (RFC 8247 as updated by RFC 9395), plus vendor interoperability testing. Explicitly identify any fallback suites and why they are justified; do not enable legacy/weak algorithms by default.

### D5 — Server certificate lifecycle and profile trust

**Decision direction.** Use an X.509 certificate with DNS SAN matching the configured hostname (illustrative: `vpn.hypervault.biz`, only if domain control is confirmed), supported key/signature algorithm, and appropriate key usage/EKU and chain for the native client. Store the private key with strict permissions and rotate in a documented procedure. The iOS `.mobileconfig` must express IKEv2 settings, server identity, EAP method and trust assumptions accurately; do not embed passwords in profiles.

**Alternatives.** Publicly trusted CA vs private CA: **undecided** until actual iOS trust/setup tests. A private CA requires deliberate trust-anchor installation; a publicly trusted certificate still needs its algorithm, EKU and IKEv2 acceptance validated. Test both during Phase 0/early Phase 1 before choosing the operational method.

**Acceptance.** Native iOS rejects wrong hostname/untrusted server; accepts valid server identity; renewal does not require unnecessary client identity changes.

### D6 — Password verifier storage and verification boundary

**Decision.** EAP-MSCHAPv2 verification consumes challenge/response values and password-equivalent secret material, rather than receiving the user's plaintext password. A standalone Argon2id/bcrypt verifier cannot validate an MSCHAPv2 NT-Response. **Do not build** `/auth/verify` around `{username,password}` as the IKEv2-daemon request.

**Phase 1:** restricted local secret store for proof of interoperability; no plaintext in source code, repository, logs or backups. Encryption-at-rest implementation/key custody requires an explicit review before exposure outside the isolated test environment.

**Phase 2:** secrets are accessible only to the authentication control-plane component. Use a verifier-material design compatible with MSCHAPv2 (typically NT hash, treated as password-equivalent). Encrypt at rest with separately controlled key material, carefully manage key backup/rotation, avoid secret-bearing debug output, enforce IPC peer authentication and restricted service identities. Password changes atomically replace verifier material.

**Suggested Phase 2 semantic IPC contract:**

```text
POST /internal/auth/mschapv2/verify
request: username, authenticator_challenge, peer_challenge,
         nt_response, protocol, authenticated_call_context
response: allowed, canonical_user_id (on success),
          mschapv2_authenticator_response (on success)
```

Validate challenge sizes, identity normalization, response derivation, mutual-auth response and failure behavior using RFC 2759 vectors; map this onto EAP-MSCHAPv2 framing in the IKEv2 daemon. The PRD's `POST /auth/verify {username,password}` is a **known specification conflict** requiring amendment, not something to implement literally.

### D7 — Addressing, routing, DNS and IPv6

**Proposed MVP:** one configurable IPv4 pool (example `10.10.10.0/24`, not reserved for every deployment), IPv4 full tunnel, one or more configurable DNS resolvers, forward/NAT via host firewall rules when egress requires it. Prevent address collisions by rejecting overlapping allocations and checking common network conflicts.

**Unresolved before Internet-facing testing:** whether to support IPv6 inside the tunnel or explicitly disable/avoid falsely claiming full-tunnel protection for IPv6 traffic. Never promise “all traffic tunneled” until IPv6 behavior is measured on iOS with Wi-Fi and cellular. Ensure split tunnel remains possible in later policy design without changing IKE state model.

**Acceptance:** route selectors, assigned address, resolver use, no unexpected DNS/IPv6 bypass for the documented mode, validated on Wi-Fi and cellular networks.

### D8 — Network and privilege boundary

**Decision.** UDP 500/4500 only for external IKEv2/NAT-T in the Phase 1 server. Enforce firewall allow rules and rate/resource limits. Use appropriate XFRM privileges (`CAP_NET_ADMIN` generally required) in a narrowly scoped adapter instead of unrestricted root access in the network-facing parser whenever feasible. The daemon must support correct NAT detection and ESP-in-UDP encapsulation, retransmissions, duplicate requests, IKE fragmentation negotiation, timers, DPD, SA deletion, cleanup and rekey before declaring the MVP robust.

**Implementation check:** decide and document whether privilege isolation uses separate helper process, Linux capabilities, or systemd confinement. A separate helper increases IPC complexity but reduces damage if the parser is exploited.

### D9 — Control-plane boundary, Phase 2 only

**Decision.** No REST/gRPC service in Phase 1. Phase 2 introduces an internal-only Rust control plane via protected Unix-domain socket (preferred) or authenticated loopback binding. `ikev2d` never reads the user database directly; `controld` never processes VPN data packets. The admin CLI uses the same protected interface. The PRD endpoint inventory remains the desired administrative interface, but the initial rollout can prioritize essential endpoints.

**Required Phase 2 behavior:** authenticated daemon-to-control-plane verifier IPC, user CRUD and password changes, user disable, active session tracking/teardown, profile generation, health/readiness, and auditing. Endpoints for backups, policy editing and artifact lifecycle can follow within Phase 2 if prioritized separately; they do not justify a public management API.

### D10 — No device concept; user-based sessions and revocation

**Decision.** There is **no device table, registration, fingerprint, per-device certificate, concurrent-device cap or per-device policy**. A user may create multiple active sessions from different systems. Sessions are operational IKE/CHILD SA instances, not device identities.

**Revocation transaction:** disable user in the authoritative store, reject subsequent authentications, enumerate all matching live sessions across daemons, request IKE deletes and removal of corresponding kernel XFRM states/policies, verify acknowledgement or reconcile if a daemon is unavailable, and audit results. “Immediate” means proactively disconnecting active sessions, not merely flagging the user disabled. Failure handling must remain explicit; a control-plane database update alone is insufficient.

## 4. Threat model (initial)

| Threat | Required countermeasure/test |
|---|---|
| Malformed or malicious IKE packets | Bounded parser, fuzz tests, reject unknown critical payloads, no panics |
| Handshake flood / resource exhaustion | Stateless cookie when necessary, queue limits, timeouts, source rate controls |
| Network MITM / rogue server | Strict certificate identity and trust validation on iOS; reject wrong SAN |
| Offline password guesses or verifier theft | Strong unique passwords; restricted/encrypted verifier material; backup and key isolation |
| Replay or stale SA | IKE message IDs, ESP replay protection, proper rekey and delete semantics |
| Credential compromise | Account disable and disconnect all sessions in Phase 2 |
| Kernel privilege abuse | Separate restricted XFRM helper or equivalent least-privilege design |
| Route/DNS/IPv6 bypass | End-to-end capture and leak tests on Wi-Fi and cellular |
| Logging secret material | Redacted logs, audit-only safe fields, no key/challenge-derived secrets in telemetry |

## 6. Architecture consequences and implementation rules

1. Use Rust traits to isolate crypto, clocks, sockets, credential verifier and XFRM commands; strict structured parsing and safe buffer limits.
2. Never write custom block cipher, hash or elliptic-curve cryptographic primitives; rely on established libraries.
3. Isolate live protocol state from persistent user identity; authenticate first, then register an established session.
4. No anonymous or partially authenticated CHILD_SA to kernel.
5. Make XFRM create/delete idempotent where possible; roll back partial operations; reconcile after crashes.
6. Treat profile generation as configuration distribution, not credential/device binding.
7. Test packet interoperability using real native iOS clients as early as possible; RFC conformance alone is insufficient.
8. Review the password-verifier security model before using real user credentials or exposing the service publicly.
