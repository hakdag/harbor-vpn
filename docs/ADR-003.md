# ADR-003 — IKE_AUTH, Server Certificates & Password Authentication

- **Project:** Custom Rust VPN Platform (iOS first)
- **Status:** ACCEPTED — owner-approved architectural policy; deployment/interoperability gates remain open
- **Version:** 1.0
- **Date:** 2026-10-18
- **Related:** PRD v0.3; TDD v0.2; ADR-001 v1.0; ADR-002 v1.0; Milestone 2 iOS packet-capture evidence

## 1. Context and constraints

Milestone 2 successfully progressed from a native iPhone `IKE_SA_INIT` request/response on UDP 500 to the client's encrypted `IKE_AUTH` request on UDP 4500. The iPhone later retransmitted `IKE_AUTH` because our responder does not implement it. This is evidence of initial-exchange interoperability, **not** server authentication or a working VPN.

Locked product requirements:

- Own Rust IKEv2 responder with Linux XFRM for future ESP; separate daemons; no third-party VPN server.
- Native iOS client first, Windows later.
- **Client authentication is permanently username/password with EAP-MSCHAPv2.**
- Server authenticates itself using an X.509 certificate and an IKEv2 AUTH signature; **not TLS**.
- No client certificates, device registration, per-device credentials or concurrent-device restrictions.
- Phase 1 permits local/file-backed credentials. The central control plane and its internal API arrive in Phase 2.
- No production rollout or public, unrestricted exposure from this ADR alone.

## 2. Accepted architectural decisions

### AUTH-01 — Standard IKEv2 certificate-authenticated responder and EAP user authentication

**Decision: ACCEPTED.** Implement RFC 7296's ordinary certificate-authenticated EAP exchange (not RFC 5998 EAP-only responder authentication):

1. Decrypt and authenticate inbound `SK` payloads using keys negotiated in `IKE_SA_INIT`, respecting initiator/responder key direction, AEAD nonces, integrity tags and message IDs.
2. Validate initial IKE_AUTH request shape, `IDi`, optional `IDr`, `CERTREQ`, initial CHILD proposal/traffic selectors as syntactic inputs, and peer exchange ordering.
3. Return responder `IDr`, the server's X.509 chain as appropriate, **server signature AUTH**, and EAP request messages inside protected IKE_AUTH exchanges. The client must authenticate the server before relying on password exchange.
4. Run EAP Identity as needed and EAP-MSCHAPv2 challenge, response, mutual authentication and success/failure, using correct EAP/IKE sequencing and message-ID increments.
5. Validate the final EAP-derived IKE AUTH confirmation, including the MSK-based AUTH calculations where required by RFC 7296. **EAP Success alone does not establish an authenticated IKE SA.**
6. Transition to `AUTHENTICATED` only after final IKE AUTH checks succeed. Do not grant an IP address, route, DNS setting, or traffic forwarding before that point.

Do not implement RFC 5998 EAP-only mode, client-certificate authentication, password-in-JSON IKE authentication, PSK-based client auth, or fallback to weaker cryptography. Do not label a successful signature or EAP challenge as completed VPN establishment.

**Scope boundary:** To finish an ordinary native iOS VPN connection, the responder must eventually negotiate and install the first CHILD_SA and configuration payloads. Keep ESP/XFRM, address allocation and forwarding for later milestones. If Milestone 3 stops after authenticated IKE state, the iPhone may still fail to connect; test cryptographic/EAP stages with isolated harnesses and captures, without claiming an operational tunnel.

### AUTH-02 — Server identity, certificate and signing algorithm

**Decision: ACCEPTED — public CA trust strategy.**

- Use `vpn.hypervault.biz` as the intended server identity **only after verifying DNS control and hostname reachability**.
- Certificate must be valid for that DNS name in the Subject Alternative Name (SAN), and the profile `RemoteIdentifier` must match it. Never disable certificate validation to get the iPhone to connect.
- Validate server certificate lifetime, chain, key usage / extended key usage where applicable, and IKE signature algorithm compatibility against the actual iOS build.
- Start with a conventional **RSA 3072-bit** server-signing key and SHA-256-based IKEv2 signature support, subject to exact RFC 7296 / RFC 7427 payload-format negotiation and observed Apple compatibility. Do not assume that an OpenSSL signature API output can be sent directly as an IKE AUTH payload without protocol framing.
- Isolate private-key loading and signing behind an interface; read key files with restricted permissions; never log keys, signature inputs, decrypted protected payloads or password material. Support certificate-chain inclusion as required.
- No client-side certificate is issued or required.

**Selected trust strategy: Publicly trusted CA.** Obtain or reuse a publicly trusted certificate for `vpn.hypervault.biz` **only after** checking server-auth suitability for native iOS IKEv2, SAN, EKU/key usage (including any IPsec-specific requirement), trust chain, IKE AUTH signature encoding, and renewal workflow. Public WebPKI trust alone does not guarantee iOS will accept it for IKEv2. Do not fall back to a private CA, self-signed certificate, disabled verification, or weaker signing algorithms without a new decision. If an appropriate public certificate cannot be issued or accepted, STOP and bring back evidence for architectural review.

**Do not assume the existing HTTPS/SSTP certificate automatically meets IKEv2 requirements.** Reuse is conditional on verifying issuer trust, SAN, usages, signing key permissions and profile behavior.

### AUTH-03 — EAP-MSCHAPv2 verifier representation and storage

**Decision: ACCEPTED — risk-aware local verifier design for Phase 1.**

- Standard one-way Argon2id/bcrypt hashes **cannot** verify the MSCHAPv2 challenge-response by themselves: the daemon never receives the plaintext VPN password through EAP.
- MSCHAPv2-compatible verification requires sensitive password-equivalent material (typically an NT hash), or an interoperable authenticated backend that possesses an equivalent verifier.
- For our single-server Phase 1 proof of concept, store an **encrypted NT-hash-equivalent verifier** per username using a well-reviewed authenticated-encryption library. Keep the distinct encryption master key outside the credential file, with restrictive OS file permissions, and a documented backup and rotation process. Reject unencrypted production storage.
- Distinguish application-layer encryption **at rest** from its necessary decryption during verification; even encrypted NT hashes remain password-equivalent secrets when accessible to a compromised process. Protect the master key separately. A local OS-root compromise cannot be cryptographically prevented by application file permissions alone.
- Use independently verified RFC 2759 test vectors for challenge hashes, NT response, authenticator response and keying material; include successful and failed authentications and identity binding. Prefer a well-reviewed MSCHAPv2 primitive/provider rather than writing DES/MD4 primitives ourselves. MSCHAPv2 itself has inherent offline password-guessing risk; require long random passwords and enforce server-authentication validation.
- Phase 2's control plane replaces the local verifier with an internal protected challenge-response verification contract, **not** `/auth/verify` accepting the user's plaintext password. Maintain revocation based on user identities and all active sessions; no device concept.

**Key custody decision (Phase 1 lab):** Use a separate, root-owned `0600` master-key file outside the repository and credential data, with access explicitly restricted to the daemon service identity as needed. Do not run the long-lived daemon as unrestricted root merely to read the key: arrange secure provisioning or a restricted service-credential mechanism when deploying. Document backup/rotation and fail closed if files are missing, exposed or corrupt. A systemd credential mechanism may replace the file later with explicit review. Neither approach is HSM-grade protection.

### AUTH-04 — Session state, failures and resource security

**Decision: ACCEPTED.**

- Add explicit post-INIT handshake states (`AWAIT_AUTH_REQUEST`, `SERVER_AUTH_SENT`, `EAP_IN_PROGRESS`, `AWAIT_FINAL_AUTH`, `AUTHENTICATED`, `FAILED`); names may vary, invariants must not.
- Enforce correct SPI/tuple/state checks, message ID windows, direction, request-response pairing, bounded retransmission response cache and duplicate EAP request handling.
- Enforce cryptographic integrity/tag verification **before parsing or acting on plaintext**, with no secret-bearing error detail and no acceptance of malformed ciphertext.
- Bind identities, negotiated key schedule, EAP results and final IKE AUTH to the same initial exchange. Reject mixed-session packets, replays, out-of-order messages and unexpected authentication methods.
- Keep bounded handshake memory, work admissions, per-user failed-auth cooldowns and globally bounded diagnostic sampling. Avoid exposing username existence or timing differences where practical.
- On timeout/failure, clear pending state and ephemeral keys; do not create CHILD_SAs or authorization side effects. Protect private-key and verifier operations; zeroize controlled transient buffers where practicable, without claiming total OpenSSL/OS-memory erasure.
- Preserve the accepted Milestone 2 UDP 500/4500 framing, suite, NAT logic and source-restricted lab safeguards. No expansion of publicly reachable services until review.

## 3. Suggested Rust implementation boundaries

```text
ikev2-wire      encrypted-payload framing; typed IKE_AUTH / EAP / CERT / ID / AUTH structures
ikev2-crypto    authenticated SK encode/decode; signature provider; EAP key derivation primitives
ikev2-core      exchange-state machine, transcript binding, message IDs, response/retry handling
vpn-auth        Phase 1 local EAP-MSCHAPv2 verifier and protected credential storage
ikev2-transport existing UDP framing, metrics and bounded dispatch
ikev2d          configuration and dependency wiring; no database or public management API
```

Use the existing workspace conventions rather than creating unnecessary layers. No control-plane HTTP service in Milestone 3.

## 4. Proposed Milestone 3 checkpoints and acceptance criteria

1. **Protected IKE codec:** decrypt/encrypt SK with independent vectors; reject tampered header AAD/tag/nonce, truncation and wrong directions; fuzz parser boundary.
2. **Server identity:** build valid CERT / IDr / signature AUTH; verify offline transcript signature and native iOS server-cert trust behavior; wrong SAN, chain, signature, key usages and expired cert fail.
3. **EAP-MSCHAPv2:** independently tested challenge-response and mutual-authenticator verification; success/failure and final IKE AUTH/MSK binding; no secret disclosure.
4. **Handshake state:** round-trip and negative tests including retransmission, expiry, replay, malformed EAP, wrong message IDs, duplicate IKE_AUTH and wrong identity.
5. **Native iPhone lab:** restricted UDP 500/4500, known disposable account and matching certificate; packet capture confirms authenticated EAP/IKE stages if reachable. Mark incomplete CHILD_SA separately; do not describe VPN as connected until tunnel setup later.
6. **Validation:** rustfmt, Clippy with warnings denied, workspace tests, independent golden vectors and new fuzz smoke; final sanitizer campaigns and target-Ubuntu OpenSSL checks before release. Retain reports with captured iOS build and source hashes.

Exit condition for Milestone 3 should be **a cryptographically authenticated IKEv2 state backed by verified server identity and EAP password authentication**, not encrypted IP transport.

## 5. Decision register and open verification gates

| ID | Approved resolution | Status / remaining gate |
|---|---|---|
| AUTH-01 | RFC 7296 certificate-authenticated responder, EAP-MSCHAPv2, no RFC 5998 EAP-only mode | **Accepted**; implement and test full multi-round IKE_AUTH + final EAP-derived AUTH |
| AUTH-02 | Publicly trusted CA; `vpn.hypervault.biz` SAN/RemoteIdentifier; RSA-3072/SHA-256 as initial candidate | **Accepted as policy**, but **certificate issuance, actual iOS trust/EKU/signature interoperability are unverified**. Stop if incompatible. |
| AUTH-03 | Encrypted NT-hash-equivalent verifier; distinct root-owned `0600` lab key file; no plaintext password in VPN daemon API | **Accepted**; implementation requires strong secret handling and independent MSCHAPv2 vectors |
| AUTH-04 | Bounded, fail-closed IKE_AUTH/EAP state machine, replay and duplicate handling, cleanup | **Accepted**; acceptance requires negative, fuzz and native lab tests |

**Implementation authorization boundary:** This ADR authorizes Codex to implement the *Milestone 3 components* after reviewing source/test context, but **does not authorize public deployment**, silent changes to cryptographic policies, private CA fallback, client certificates, device limits, Phase 2 control plane, CHILD_SA installation, XFRM, IP routing, DNS or forwarding.

**Acceptance boundary:** Native-client evidence must distinguish successfully negotiated IKE_SA_INIT from successful server certificate verification, EAP authentication, and final IKE AUTH confirmation. A native iPhone may still report failed VPN connection because the initial CHILD_SA is intentionally excluded. Evidence from packet traces alone cannot reveal or conclusively prove decrypted EAP results; use sanitized daemon state and independent test harnesses.
