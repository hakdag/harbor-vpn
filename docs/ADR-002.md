# ADR-002 — IKE_SA_INIT Cryptography and Handshake Policy

- **Project:** Custom Rust VPN Platform (iOS-first)
- **Date:** 2026-10-17
- **Status:** Accepted (2026-10-17); interoperability-dependent details remain subject to validation
- **Scope:** Milestone 2 only — IKE_SA_INIT responder foundation
- **References:** PRD v0.3; TDD v0.2; ADR-001; Milestone 1 verification; RFC 7296, RFC 8247; Apple IKEv2 profile documentation

## Context

Milestone 1 delivered a bounded, offline IKEv2 codec. Milestone 2 needs a narrowly defined crypto profile, provider boundary, and safe responder handshake behavior. It does **not** implement IKE_AUTH, user authentication, CHILD_SA/ESP, Linux XFRM, or the Phase 2 control plane. A successful IKE_SA_INIT is **not an authenticated VPN connection**.

## Decision INIT-01 — IKE SA cryptographic proposal

**Approved initial profile (one selectable suite):**

| Transform | Choice | IKEv2 identifier/notes |
|---|---|---|
| Encryption | AES-256-GCM, 16-byte tag | `ENCR_AES_GCM_16` (20), key length attribute 256 |
| PRF | HMAC-SHA-256 | `PRF_HMAC_SHA2_256` (5) |
| Integrity | None as a separate transform for AEAD | Do not offer an integrity transform with AES-GCM; authenticated encryption supplies integrity |
| DH | ECP-256 / NIST P-256 | Group 19 |

- Parse and preserve other numeric offers, but **select only fully implemented and explicitly enabled suites**. If there is no intersection, return the standards-appropriate error without negotiation downgrade.
- Do not silently fall back to SHA-1, MD5, 3DES, weak MODP groups, or unauthenticated encryption.
- Maintain a policy representation that can add a *separately reviewed* compatibility suite later, if native iOS testing requires it. A possible AES-CBC + HMAC-SHA2 alternative is **not approved** by this ADR.
- Cipher support in Apple's configuration documentation is evidence of configurability, **not proof that a particular iOS build offers the exact suite by default**. A `.mobileconfig` test profile must explicitly request the intended IKE SA parameters. Record iOS build and the actual SA proposal seen on the wire.
- ESP/CHILD_SA crypto is **not decided here**.

## Decision INIT-02 — Cryptography provider and key handling

**Approved provider:** Use the Rust `openssl` crate against a supported, maintained OpenSSL 3.x `libcrypto` on the target Ubuntu LTS host, behind a **project-owned `ikev2-crypto` trait/interface**. This is an implementation recommendation, not permission to embed third-party VPN server software.

Provider responsibilities:

- CSPRNG generation via OS-backed OpenSSL random facility.
- Fresh ephemeral ECDH P-256 keypair for each new handshake; validate peer public points and reject invalid or point-at-infinity input.
- AES-256-GCM encrypt/decrypt with authenticated header/AAD handling and correct nonce/IV uniqueness; no custom primitive implementation.
- HMAC-SHA-256 PRF and RFC 7296 `prf+` derivation; use protocol-specific labels, nonce ordering, SPI ordering and truncation exactly as specified.
- Tests against independent key derivation vectors and invalid point/ciphertext cases.

Safety boundaries:

- No hand-written cryptographic primitives and no raw secret values in logs, errors or debug traces.
- Minimize lifetime of ephemeral secrets and derived keys. Zeroize application-owned sensitive buffers where feasible; do not claim that allocator or FFI internals are comprehensively zeroized.
- No deterministic keys or IVs outside tests. Use fixed test vectors only under test configuration.
- Keep the provider replaceable; record exact crate/OpenSSL versions and target-host linkage in the build evidence.
- Perform a brief license/deployment review before Ubuntu production packaging.

**Alternative considered:** RustCrypto composition for AES-GCM, P-256, HMAC and randomness. It is reasonable but raises integration and maintenance surface for this first implementation. Provider choice can be reconsidered with a benchmark/security review; changing it requires an ADR update.

## Decision INIT-03 — Initial handshake and transport policy

**State machine:** Stateless initial request validation where possible; allocate bounded pending state only after structural and policy checks. A preliminary `IKE_SA_INIT` response does **not** mark a user authenticated.

**Initial transport scope:**

- Implement UDP 500 first on IPv4 with explicit packet-size limits and nonblocking reads.
- Prepare a separable UDP 4500 path for NAT-T (4-byte non-ESP marker for IKE packets) before claiming compatibility from NATed iPhones. Complete NAT detection and UDP 4500 handling in this milestone before any native-iOS interoperability exit criterion is accepted.
- Do not assume native iOS compatibility based only on local codec tests; test behind a real NAT as well as on direct networking.
- No MOBIKE or IKE fragmentation advertisement until implemented and tested. Neither is silently assumed.

**Responder checks and resource bounds:**

- Strict IKEv2 version/exchange-type/flags/message-ID/SPI validation for an initial initiator request, plus required payload set and protocol-specific KE group validation.
- Only negotiate a configured suite; produce correct `INVALID_KE_PAYLOAD`, `NO_PROPOSAL_CHOSEN`, and other RFC-defined errors where applicable.
- Fresh responder SPI and cryptographically secure nonce; check ECDH public keys and all cryptographic lengths.
- Bound total pending handshakes, per-source pending entries, response bytes, and per-handshake lifetimes. Initial **candidate policy**: 10-second pending lifetime; 1,024 global pending entries; 32 per source IP. These are safety caps, **not limits on authenticated users, devices, or concurrent VPN sessions**. Expose via validated config with conservative hard ceilings and tune using tests.
- Respond deterministically to duplicate IKE_SA_INIT requests using an idempotent cache for a bounded time; no duplicate ECDH allocation for identical pending requests. Initiators normally retransmit requests; the responder must handle retransmission safely.
- Add an RFC 7296 COOKIE mechanism under load, with server-secret rotation and verification tied to request context, to avoid expensive crypto allocation before address validation. Exact activation thresholds and cookie encoding require implementation design and test evidence.
- Implement NAT_DETECTION_SOURCE_IP / NAT_DETECTION_DESTINATION_IP correctly, including hashing and address/port association according to RFC 7296.
- Bind only to required ports; document Ubuntu socket privileges and systemd sandboxing before the live listener runs. Binding UDP 500 typically needs capability handling; do not run the process with unrestricted root privileges by default.
- Log metadata only: request count, selected transform IDs, retry/cookie outcomes, rejection categories, pending count and latency. Never log keys or packet secrets.

## Boundaries and dependencies

The following are **out of scope** and are not implicitly approved by this record:

- IKE_AUTH, certificate signing/authentication, EAP-MSCHAPv2, user store and password verifier.
- CHILD_SA, ESP transforms, virtual IP, routes, DNS, Linux XFRM and traffic forwarding.
- Phase 2 administrative APIs, device registration, or device/session restrictions.
- Production-grade rekey/DPD/MOBIKE and fragmented IKE payload handling.

## Acceptance plan for Milestone 2

1. **Offline exchange tests:** golden request/response fixtures; supported and unsupported proposals; invalid KE; invalid SPI/flags/IDs; P-256 point validation; duplicates and correct nonce/key derivation with independent vectors.
2. **Security tests:** bounded state and memory under bursts; responder cookie path under simulated load; no panic; no key material in diagnostics.
3. **Live lab tests:** UDP 500 and UDP 4500 response handling; NAT detection; packet captures excluding secrets; independently verify parser/exchange behavior against an established standards-compliant client or test harness.
4. **iOS compatibility evidence:** record iOS version/build and explicit `.mobileconfig` cryptographic settings, verify the offered algorithms and successful IKE_SA_INIT including a NATed connection. This **does not** prove IKE_AUTH or end-to-end VPN success.
5. `cargo fmt`, `cargo clippy`, `cargo test`, negative/property tests and targeted fuzzing pass; no regressions in Milestone 1.

## Owner approval and implementation authorization boundary

**Approved on 2026-10-17:**

- **INIT-01:** AES-256-GCM-16 (`ENCR_AES_GCM_16`, key length 256), `PRF_HMAC_SHA2_256`, ECP group 19; no separate integrity transform with AEAD, and no silent weaker fallback.
- **INIT-02:** Rust `openssl` crate backed by supported OpenSSL 3.x, isolated behind project-owned `ikev2-crypto` interfaces.
- **INIT-03:** IPv4 UDP 500 and NAT-aware UDP 4500 for IKE_SA_INIT, correct non-ESP marker and NAT detection, bounded responder state, retransmission behavior and RFC COOKIE defense.

**Approval scope:** Authorizes planning and implementation of **Milestone 2 only**, subject to normal code review and acceptance testing. It does not authorize IKE_AUTH, credential or certificate authentication, ESP/CHILD_SA, XFRM, production deployment, new client identifiers or restrictions, or the control plane.

**Validation still required:** Confirm actual native iOS proposals, accepted profile settings, NAT behavior, and relevant host/runtime privileges in test environments. The preliminary pending-handshake capacity/time defaults and cookie thresholds are tunable implementation candidates, not claims of standard-required values. Record test evidence before claiming interoperability.

**Security note:** IKE_SA_INIT derives unauthenticated IKE keys; it does not authenticate either party or create a usable VPN. The responder must not describe an IKE_SA_INIT success as authenticated client access.

**Revision rule:** A different suite, crypto provider or materially changed handshake/transport policy requires documented owner review and ADR amendment.
